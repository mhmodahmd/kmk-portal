# 01 — المعمارية

> الحالة: **مسودة للاعتماد** · آخر تحديث: 2026-11-14

## 1. الفكرة في سطر

نظام واحد باسم **بوابة KMK**: واجهة سريعة مستضافة على **GitHub Pages**، تتصل بخادم واحد على **Google Apps Script**، يقرأ ويكتب في **Google Sheets** ويحفظ المرفقات في **Google Drive**. النظام مقسّم إلى **نواة مشتركة** و**وحدات مستقلة** يمكن إضافتها لاحقاً دون المساس بغيرها.

```
 المتصفح / الجوال (PWA)
 ┌────────────────────────────────────────┐
 │ web/  واجهة React على GitHub Pages     │  تُحمَّل فوراً، تحفظ آخر البيانات محلياً
 └───────────────────┬────────────────────┘
                     │ HTTPS POST  (JSON)
 ┌───────────────────▼────────────────────┐
 │ server/  Apps Script Web App           │  جلسة ← صلاحية ← منطق ← تدقيق
 │  core/  +  modules/<وحدة>/              │
 └───────────────────┬────────────────────┘
 ┌───────────────────▼────────────────────┐
 │ Google Sheets: ملف للنواة + ملف لكل وحدة│
 │ Google Drive:  مجلد مرفقات لكل وحدة     │
 └────────────────────────────────────────┘
```

## 2. لماذا هذه البنية

| القرار | السبب |
|---|---|
| الواجهة على GitHub Pages | تحميل فوري من CDN، بدل انتظار Apps Script لبناء الصفحة في كل مرة. تحديد الموقع والكاميرا يعملان بلا قيود iframe. |
| الخادم على Apps Script | مجاني، متكامل مع Sheets و Drive، والنظامان الحاليان مبنيان عليه. |
| البيانات على Sheets | مناسب لحجم شركة بفرع واحد، والإدارة تستطيع رؤية البيانات مباشرة. |
| وحدة واحدة = مجلد + ملف بيانات | حدود واضحة بين الوحدات، وأي وحدة يمكن تطويرها أو إيقافها وحدها. |
| طبقة بيانات واحدة (`Db`) | لو احتجنا قاعدة بيانات حقيقية لاحقاً (Supabase مثلاً) نغيّر هذه الطبقة فقط. |

## 4. الخادم (server/)

### 4.1 النشر
- مشروع Apps Script **مستقل** (غير مرتبط بملف Sheet)، يُنشر Web App بإعداد:
  `Execute as: Me` · `Who has access: Anyone`.
- الوصول "للجميع" ضروري لأن الواجهة على نطاق آخر. **الحماية الحقيقية في الخادم**: كل إجراء يتحقق من الجلسة والصلاحية، كما في النظامين الحاليين.
- معرّفات ملفات البيانات ومجلدات Drive تُحفظ في **Script Properties** (`CORE_DB_ID`, `ATT_DB_ID`, …) لا في الكود.
- المنطقة الزمنية الموحدة: `Asia/Kuwait`.

### 4.2 مسار الطلب
```
doPost(e)
  └─ Router.handle({ action, token, payload, v })
       1. فك JSON والتحقق من الشكل
       2. إن لم يكن الإجراء عاماً: Auth.requireSession(token)
       3. Permissions.assert(user, route.module, route.permission)
       4. route.fn(ctx, payload)        ← منطق الوحدة
       5. Audit.log(...) للإجراءات التي تُعدّل البيانات
  └─ ContentService JSON  { ok, data } | { ok:false, error:{ code, message } }
```

- أسماء الإجراءات بصيغة `وحدة.إجراء`: `custody.list`, `hr.leave.request`, `crm.customer.save`.
- كل وحدة تسجّل إجراءاتها في جدول توجيه واحد (نفس فكرة `apiRoutes_` في نظام العهد):
  ```js
  Router.register('custody', {
    'custody.list':    { perm: 'custody.view',    fn: Custody.list },
    'custody.approve': { perm: 'custody.review',  fn: Custody.approve, write: true },
  });
  ```
- **إجراء مجمّع** `batch` ينفذ عدة إجراءات في طلب واحد، و**إجراءات ملخّص** لكل شاشة كبيرة (مثل `home.summary`) لتقليل عدد الطلبات.

### 4.3 النواة (server/core)
| الملف | المسؤولية | المصدر |
|---|---|---|
| `Router` | التوجيه، الأخطاء الموحدة، `batch` | `Code.js` في العهد |
| `Auth` | الدخول، الجلسات، تذكّر الجهاز، قفل الحساب، تغيير كلمة المرور | `Auth.js` في العهد |
| `Db` | قراءة وكتابة الجداول بأسماء الأعمدة، الأنواع، القفل، الأرقام التسلسلية، التخزين المؤقت | `Db.js` في العهد، مع دعم عدة ملفات |
| `Permissions` | أدوار لكل وحدة + نطاق البيانات | جديد |
| `Audit` | سجل كل تعديل | `logAudit` في العهد |
| `Settings` | إعدادات الشركة والقوائم القابلة للتعديل | `Settings.js` في العهد |
| `Files` | رفع المرفقات إلى Drive وقراءتها | `Archive.js` في العهد |
| `Notify` | إشعارات داخل النظام + بريد اختياري. تُبنى من `Audit.log`: «بانتظار قرارك» بقواعد `inbox_` نفسها، ونتائج الطلبات من `notify_` في كل وحدة | ✅ 0.8.0 |
| `Inbox` | تجميع "ما ينتظر قراري" من كل الوحدات | جديد |
| `Utils` | المبالغ بالفلس، التواريخ، التحقق من المدخلات، التفقيط | `Utils.js` و `Vouchers.js` في العهد |

### 4.4 قواعد الوحدات
1. الوحدة تكتب **في ملف بياناتها فقط**.
2. لا تقرأ وحدة جداول وحدة أخرى مباشرة، بل تستدعي **واجهتها العامة** (مثلاً `Hr.public.employee(id)`).
3. لأن Apps Script يضع كل الدوال في نطاق واحد، كل وحدة تُكتب **ككائن باسمها** (`Custody`, `Hr`, `Crm`…) والدوال الداخلية تنتهي بـ `_`.
4. كل وحدة تقدّم للنواة:
   - `routes` إجراءاتها وصلاحياتها
   - `schema` جداولها
   - `inbox(user)` ما ينتظر قرار المستخدم فيها
   - `search(user, q)` نتائجها في البحث الشامل
   - `summary(user)` بطاقتها في الشاشة الرئيسية
5. **الأحداث بين الوحدات** عبر `Events.emit('hr.employee.terminated', {...})`، وكل وحدة تشترك فيما يهمها. مثال: العهد ترفض المخالصة إن كانت على الموظف عهدة مفتوحة.

### 4.5 البيانات
- ملف Google Sheet لكل وحدة: `KMK-Core`, `KMK-Attendance`, `KMK-HR`, `KMK-Custody`, `KMK-Tasks`, `KMK-CRM`, `KMK-Finance`.
- كل جدول له مخطط (أسماء الأعمدة وأنواعها) في الكود، ويُنشأ تلقائياً عند الإعداد.
- معرّف داخلي فريد لكل سجل، ورقم مقروء عند الحاجة (`NTH-2026-014`, `PV-2026-0007`, `INV-2026-0031`).
- المبالغ تُحسب داخلياً **بالفلس** (أعداد صحيحة) لتجنب أخطاء الكسور، وتُعرض بثلاث خانات عشرية.
- **أرشفة سنوية** للحركات القديمة في ملف منفصل لتبقى الجداول خفيفة.

## 5. الواجهة (web/)

### 5.1 التقنيات
| المجال | الاختيار |
|---|---|
| الإطار | React + TypeScript + Vite |
| التنسيق | Tailwind CSS بمتغيرات الهوية (انظر 02) واتجاه RTL كامل |
| المكونات | مكتبة داخلية في `web/src/ui` مبنية على Radix UI (سهولة الوصول ولوحة المفاتيح) |
| التوجيه | React Router بنمط `HashRouter` (يعمل على GitHub Pages دون إعدادات خادم) |
| بيانات الخادم | TanStack Query: تخزين مؤقت، تحديث في الخلفية، استجابة متفائلة |
| النماذج | React Hook Form + Zod للتحقق |
| التواريخ | Day.js بتوقيت الكويت |
| الرسوم البيانية | Recharts عند الحاجة |
| الأيقونات | Tabler Icons |

### 5.2 الاتصال بالخادم
```ts
api('custody.list', { status: 'open' })
// POST <API_URL>
// Content-Type: text/plain;charset=utf-8   ← يتجنب طلب CORS المسبق
// body: {"action":"custody.list","token":"…","payload":{…},"v":"1.4.0"}
```
- رمز الجلسة يُرسل داخل الطلب لا في الترويسات، لأن Apps Script لا يدعم طلبات CORS المسبقة.
- عند `SESSION_EXPIRED` تحاول الواجهة الاستئناف برمز الجهاز، وإلا تعرض شاشة الدخول وتعود بعدها للمكان نفسه.
- رقم إصدار الواجهة `v` يُرسل مع كل طلب، والخادم يطلب التحديث إن كان الإصدار أقدم من المسموح.

### 5.3 السرعة
1. **الهيكل يُحمَّل فوراً** من GitHub Pages ويُخزَّن عبر Service Worker.
2. **تحميل كل وحدة عند فتحها فقط** (code splitting).
3. **طلب واحد لكل شاشة** عبر إجراءات الملخّص و `batch`.
4. **عرض آخر بيانات محفوظة فوراً** ثم تحديثها في الخلفية.
5. **استجابة متفائلة** للإجراءات (موافقة، إكمال مهمة)، مع التراجع إن فشل الطلب.
6. **ضغط الصور على الجهاز** قبل رفعها (صور الفواتير من الكاميرا).
7. **جلب مسبق** للشاشة التالية المتوقعة عند المرور على الرابط.
8. هدف الأداء: الواجهة تظهر خلال **أقل من ثانية**، والبيانات المحفوظة تظهر فوراً، والبيانات الحية خلال **ثانية إلى ثانيتين**.

### 5.4 تطبيق قابل للتثبيت (PWA)
- اسم التطبيق "KMK"، وأيقونته السهم `>` من الشعار.
- يعمل بملء الشاشة على الجوال. لا يعمل دون اتصال للتعديلات (الحضور يحتاج وقت الخادم وموقعه).

## 6. الأمان
- كلمات المرور SHA-256 مع salt، وقفل الحساب بعد 5 محاولات، وجلسة 6 ساعات، وتذكّر الجهاز 30 يوماً بتوقيع HMAC (كما هو الآن).
- **كل إجراء يتحقق من الصلاحية في الخادم**. إخفاء الأزرار في الواجهة للراحة فقط.
- لا أسرار في كود الواجهة. عنوان الخادم معروف لكنه لا يعطي شيئاً دون جلسة.
- Content-Security-Policy في الواجهة لتقليل خطر حقن السكربتات.
- سجل تدقيق لكل تعديل: من، ماذا، متى، القيمة قبل وبعد.
- روابط توقيع المدير تُحفظ ببصمتها لا بنصها، ولها مدة صلاحية (كما هو الآن).
- **الوقت والموقع للحضور يُعتمدان من الخادم**، لا من جهاز الموظف.

## 7. حدود Apps Script وكيف نتعامل معها
| الحد | الأثر | المعالجة |
|---|---|---|
| 6 دقائق للتنفيذ | التقارير والاستيراد الكبير | التقسيم على دفعات بمشغلات زمنية |
| 30 تنفيذاً متزامناً (لأن الكل ينفذ باسم المالك) | ضغط لحظي عند بداية الدوام | يكفي لفريق شركة بفرع واحد، والتخزين المؤقت يقلل الطلبات |
| بطء Sheets مع كبر الجداول | تثاقل بمرور السنوات | ملف لكل وحدة + أرشفة سنوية + تخزين مؤقت |
| زمن الطلب 1–2 ثانية | انتظار | أساليب السرعة في 5.3 |
| حجم الطلب | المرفقات الكبيرة | حد 10MB للملف وضغط الصور مسبقاً |

**متى نفكر في الانتقال من Sheets؟** إذا تجاوز أي جدول نشط عشرات الآلاف من الصفوف، أو زاد المستخدمون المتزامنون كثيراً. وبفضل طبقة `Db` يقتصر التغيير على الخادم.

## 8. البيئات والنشر
| | التجريبية (dev) | الإنتاج (prod) |
|---|---|---|
| الخادم | مشروع Apps Script تجريبي | مشروع Apps Script الإنتاج |
| البيانات | ملفات Sheets تجريبية | ملفات الشركة الحقيقية |
| الواجهة | تعمل محلياً (`npm run dev`) | GitHub Pages من فرع `main` |

- نشر الواجهة **تلقائي** عبر GitHub Actions عند الدمج في `main`.
- نشر الخادم بـ `clasp push` ثم إصدار نشر جديد، **ولا يُنشر للإنتاج إلا بموافقتك**.
- الاختبارات: اختبارات الخادم داخل Apps Script (كما في `Tests.js`) + محاكي محلي، واختبارات للواجهة قبل النشر.
